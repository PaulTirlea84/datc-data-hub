    Data Engineering

    The Data Engineering domain covers back-end data infrastructure within the DATC Data Platform. Practitioners in this domain construct, optimize, and maintain the infrastructure for data generation, transformation, and storage. They design pipelines, workflows, and data platforms that facilitate the seamless flow of data across systems — feeding the Analytics domain and client AI applications with clean, reliable, well-governed data.

    AI extends this domain rather than replacing it. AI assistants accelerate engineering work, and data agents — goal-driven systems that use metadata, lineage, policies, and approved tools to perform or coordinate data work — are becoming the most relevant AI capability for Data Engineering. The engineer remains accountable for correctness, security, reliability, and business fitness of every data product, regardless of whether an artefact was written by hand, generated by an assistant, or produced by an agent.

    What Data Engineering Does

    • Data Engineering

      Construct and maintain infrastructure for data generation, transformation, and storage. Design pipelines and data platforms for seamless data flow. Own the full ETL/ELT cycle from raw ingestion through to analytics-ready layers.

    • Data Architecture

      Define and align the major types and sources of data necessary to support the business. Determine how data is used, stored, managed, and integrated within IT systems. Design lakehouse, DWH, and hybrid architectures that scale.

    • Modern Data Management & Governance

      Implement strategies for collecting, storing, processing, and governing data in complex modern data ecosystems. Ensure data quality, security, and accessibility through lineage, cataloguing, and observability.

    • AI-Ready Data

      Build the data foundations that power GenAI applications — RAG pipelines, vector databases, embedding workflows, and semantic layers. Ensure data is clean, compliant, and structured for AI consumption.

    • Data Agents & Agentic Data Operations

      Design, build, and govern data agents that discover and profile sources, generate and optimize pipeline code, run quality and reconciliation checks, investigate failures, enrich metadata, analyse lineage impact, and optimize workloads. Agents operate with defined objectives, approved tools, bounded actions, approval gates, and full traceability.

    • DataOps & Platform Automation

      Automate the build, test, release, and operation of data assets through source control, CI/CD, infrastructure as code, automated testing, observability, and incident management — extended to cover AI-generated and agent-produced changes.

    Data Agents in Data Engineering

    Data agents are the AI capability most directly relevant to this domain. They are not chatbots and not simple copilots: an agent receives an engineering objective, plans the steps, calls approved tools, validates intermediate results, and either completes the task or escalates to a human.

    Where Data Agents Apply

    Lifecycle Stage Agent Capability Typical Outcome
    Discovery Scan sources, infer schemas, classify content, detect sensitive data Faster onboarding of new sources
    Profiling Analyse distributions, nulls, cardinality, formats, outliers Early detection of structural issues
    Development Generate SQL, dbt models, mappings, configurations, tests Reduced repetitive build effort
    Data Quality Propose and execute rules, reconcile source vs. target, detect anomalies Higher coverage of quality controls
    Operations Triage failures, analyse logs and dependencies, propose remediation Lower mean time to diagnose
    Metadata Enrich catalogue entries, align business glossary, maintain descriptions Better catalogue completeness
    Lineage Trace upstream/downstream impact of schema or model changes Safer change management
    Governance Detect policy violations, support access reviews, flag retention issues Continuous control monitoring
    Optimization Identify expensive queries, propose partitioning, clustering, sizing Cost and performance improvement
    RAG Pipelines Manage ingestion, chunking, embedding refresh, retrieval evaluation Trustworthy AI-ready data

    Agent Autonomy Tiers

    The required level of control depends on the impact and reversibility of the action, not on the seniority of the engineer.

    Tier Behaviour Data Engineering Example Required Control
    A0 — Inform Explains or summarizes Explain why a load failed User reviews the output
    A1 — Recommend Proposes an action Recommend data-quality rules Human decides
    A2 — Draft Produces an artefact Generate a dbt model or ADF configuration Code review + automated tests
    A3 — Execute with Approval Acts only after sign-off Apply an approved metadata or catalogue update Approval, logging, rollback
    A4 — Bounded Execution Acts within strict limits Retry eligible failed loads within a defined window Policy limits, monitoring, rollback
    A5 — High Autonomy Coordinates cross-system actions Autonomous workload optimization Exceptional governance + explicit authorization

    Non-Negotiable Controls

    Every data agent in production must have:

    • a documented objective and scope;
    • an accountable human owner;
    • least-privilege data and tool access;
    • deterministic validation of its output (tests, reconciliation, schema checks);
    • logging of prompts, tool calls, approvals, and resulting data changes;
    • defined escalation conditions;
    • monitoring for success rate, failure rate, latency, and cost;
    • a tested rollback or recovery path for any write action.

    Design principle

    If a task can be solved reliably with deterministic automation, use deterministic automation. Agents are for tasks that require interpretation, context, planning, or tool selection — not for replacing a scheduled job that already works.

    Level Profiles

    Each level describes the expected engineering scope, the expected use of AI and data agents, and the practical evidence that demonstrates the level. Training supports development; delivered work confirms proficiency.

    Associate (L12) — Junior Data Engineer

    Focus: understand data pipelines and databases; execute ETL tasks with close guidance.

    Responsibilities

    • Understand the DWH architecture and data flow end-to-end
    • Learn team procedures, roles, and delivery standards
    • Write and maintain SQL scripts for data extraction and transformation
    • Implement ETL mappings and loaders based on provided designs
    • Execute and monitor daily pipeline runs; handle basic errors
    • Validate data between source, staging, and target layers
    • Support data quality checks and reconciliation activities
    • Work within established DWH layer structures (stage, core, semantic)
    • Update pipeline configuration files under guidance (YAML, config files)
    • Document changes in Jira; participate in stand-ups
    • Diagnose basic data issues with senior guidance

    AI & Data-Agent Expectations

    • Use approved AI assistants for draft SQL, code explanation, documentation, and troubleshooting
    • Run predefined data agents (profiling, validation, log analysis) under supervision
    • Understand the difference between an assistant, an automation, a data agent, and a RAG pipeline
    • Recognise that AI output can be plausible but wrong, incomplete, or out of context
    • Perform basic checks (row counts, sample comparison, syntax and logic review) before accepting output
    • Never let an agent write to production without senior review and approval
    • Escalate unexpected or unexplained agent behaviour immediately

    Core Skills

    • SQL: SELECT, JOIN, WHERE, GROUP BY, subqueries, basic aggregations
    • PL/SQL basics: procedures, functions, cursors
    • Understanding of ETL concepts: extract, transform, load; staging vs. target
    • DWH layer model awareness: raw, staging, core, semantic
    • Jira / Confluence: ticket creation and documentation
    • Git / SVN: basic version control — clone, commit, pull
    • Excel and basic data profiling
    • Basic AI literacy: prompting, limitations, validation, approved-tool usage

    Practical Evidence

    • A reviewed SQL or transformation script delivered to the team's standards
    • A completed source-to-target validation with documented results
    • A pipeline run executed and monitored, including handling of a basic error
    • Documentation updated in Jira or Confluence
    • One AI-assisted task with a written note on what was validated and what was corrected
    • One supervised use of a predefined data agent, with the outcome checked

    Proficiency Assessment & Evidence

    Training demonstrates preparation. Delivered work and evidence demonstrate proficiency.

    Courses, certifications, and self-assessments support development plans. They do not by themselves establish a level. The assessment answers a practical question: what has this person actually built, validated, and owned — and at what scope?

    Assessment Dimensions

    Dimension Question L12 L11 L10 L9 L8 L7
    Autonomy How much guidance is needed? Close guidance Independent on defined tasks Independent end-to-end Technical authority Owns platform decisions Owns domain direction
    Complexity How hard are the problems? Simple, well-defined Standard pipelines Complex workflows Architecture & patterns Multi-team integration Cross-platform strategy
    Scope How wide is the impact? One task One pipeline / source One solution / data product Multiple teams Portfolio / platform Domain / practice
    Impact What changed measurably? Task completed Delivery improvement Solution outcome Reusable capability Repeatable adoption Strategic outcome
    Validation How is output verified? Basic checks with help Repeatable checks Automated tests & evaluation Defines test standards Defines control standards Owns assurance model
    Governance Are controls applied? Follows rules Applies rules independently Implements controls Reviews & defines controls Enforces standards Sets principles
    Data agents What agent capability? Uses predefined agents Configures agents Designs & builds agents Architects agent patterns Integrates & scales Sets agent strategy
    Leadership Who else benefits? Learns Contributes Mentors Leads technically Coaches leads Builds capability

    Accepted Evidence

    • source code, pull requests, and code reviews;
    • pipeline and data model implementations;
    • automated test suites and reconciliation results;
    • technical designs and architecture documents;
    • agent configurations, guardrails, and evaluation reports;
    • observability dashboards, logs, and monitoring evidence;
    • deployment records and CI/CD pipelines;
    • performance before/after measurements;
    • incident reports and root-cause analyses;
    • runbooks and operational documentation;
    • reusable patterns, templates, or frameworks with proof of adoption;
    • peer, SME, architect, security, or stakeholder validation;
    • mentoring and coaching outcomes.

    Client-confidential evidence must be redacted or reviewed through an approved restricted process.

    Evidence Quality Criteria

    Evidence should be recent, relevant to the claimed level, attributable to the individual, independently reviewable, supported by observable outcomes, and compliant with security and confidentiality requirements.

    Assessment Rules

    1. A candidate must meet the expectations of the claimed level and all levels below it.
    2. Course completion alone never establishes a level.
    3. Tool familiarity is not the same as engineering or architecture proficiency.
    4. One successful prototype does not demonstrate platform- or domain-level capability.
    5. Evidence must show both delivery and validation — what was built and how it was proven correct.
    6. For AI-assisted work, the engineer's own decisions, review, and corrections must be visible.
    7. Production evidence is preferred; production-representative evidence is acceptable where access is restricted.
    8. The level reflects consistently demonstrated capability, not a single exceptional example.
    9. Platform-specific expertise is assessed separately from transferable engineering capability.
    10. Assessors calibrate across the team to keep levels comparable.

    Assessment Process

    1. Self-assessment — the engineer proposes a level and maps evidence to each dimension.
    2. Evidence review — the assessor checks ownership, recency, scope, validation, and outcomes.
    3. Technical discussion — the engineer explains design decisions, trade-offs, controls, and limitations.
    4. Demonstration where relevant — a walkthrough of the solution or agent, including failure handling.
    5. Calibration — comparison with peers at the same claimed level.
    6. Decision — confirmed, provisionally confirmed, or development required.
    7. Development plan — gaps converted into assignments, mentoring, and learning.
    8. Periodic review — revisited when responsibilities or evidence materially change.

    On measurement

    Measuring competency reliably is the hardest part of this framework, and the first cycles should be treated as calibration rather than final judgement. The purpose is to make expectations explicit, give people a concrete path, and improve the model based on how it behaves in real assessments.

    Framework Governance

    This framework is expected to change as it is used.

    Review triggers: after the first assessment cycle · when platform capabilities change materially · when new security, privacy, or client requirements emerge · when assessors interpret levels inconsistently · at least annually.

    Owners maintain: level definitions · evidence examples · assessor guidance · calibration sessions · the training and certification catalogue (kept separate so it can be refreshed without rewriting the career model).

    Each version records: version number · date · owner · approver · change summary · next review date.

    Initial adoption

    In the first cycles, treat proficiency decisions as calibrated development assessments rather than permanent labels. The framework exists to clarify expectations, guide learning, and build trusted capability — and it should be adjusted once real assessments show where it works and where it does not.
